# PENDENT
*A little fluid simulation, but in a pendant. And powered by an ASIC.*


So, the idea was simple.


I wanted to make a pendant with a little fluid simulation running inside it. Something that you can shake around, play with, and just look at.


I got the idea from [Mitxela's Fluid Simulation Pendant](https://mitxela.com/projects/fluid-pendant).


But I wanted to do something a little different.


Instead of just using a microcontroller to run the simulation, I wanted to make my own ASIC for it.


How hard could it be?


Well...


This is how that went.


---

## Moving to Python

I wanted to make the Python version because I had found Amaranth and started thinking about how I could eventually build the pendant as an ASIC. The Python version would let me work out the simulation first. I already knew I couldn't just convert normal Python code into hardware line by line. I would have to remake the design around hardware constraints, and I thought it would be much easier to figure out the behaviour now than while also fighting the hardware implementation.

I used:

- **Pyray** — Python bindings for Raylib, for rendering.
- **NumPy** — for the numerical calculations.

### Trying to fix the flickering

One problem I kept running into was flickering in the LED output. In some experiments, areas with fewer particles became black. The brightness was based on how many particles were in a tile: more particles meant more brightness, and zero particles meant no glow.

Because the boundary pushed particles into a roughly circular shape, the corners of the square grid could remain empty and black. I didn't immediately know what was causing every part of the flicker, so I kept changing parameters and watching what happened. Some changes helped with the flickering, but also changed the behaviour of the fluid.

For example, one set of changes made the particles move more slowly and feel heavier. That is where the honey-like behaviour came from.

## Okay, let's make an ASIC

I had already been interested in learning FPGA development before PENDENT. I wanted to make HoloCore more independent, because at the time it needed a bridge to work on its own.

I was looking around for ways to learn HDL. I watched some videos from [Nand Land](https://www.youtube.com/watch?v=fLua2urAuq0&list=PLnAoag7Ew-vr1M98Q5K2kLHxFQ5l0DU3B). They had some good videos, although I will admit I fell asleep during some of them. I wasn't planning to buy the Go board. I was mostly curious and wanted to see what HDL was about.

I also found this [visual explanation of FPGA](https://youtu.be/d3nuepnbmC4). I had seen it before, when I didn't know enough to understand much of it, and had only glanced at it. Rewatching it later made a lot more sense. It is one of the best visual explanations of FPGA that I found, and it also uses Amaranth.

Finding **Amaranth** was a game changer for someone seeing HDL for the first time. I found it before I properly learned Verilog. I had only started getting into the basics, but using Python to describe hardware made the subject feel much more approachable.

### Starting with tiny circuits

I started with the half adder. Two 1-bit inputs, A and B, and two outputs: Sum and Carry. It is a tiny circuit, but seeing it work in a test gave me that feeling that I was getting closer to actually making hardware. I had also tried building logic in [NandGame](https://nandgame.com/), so seeing the same ideas work in Amaranth was pretty satisfying.

After the half adder, I built a full adder, then a 4-bit adder. After that I moved on to fixed-point arithmetic (Q4.12) and a multiplier.

I was learning from the [Amaranth documentation](https://amaranth-lang.org/docs/amaranth/latest/). I first tried the examples online, then installed the tools in a Linux VM and set everything up there. I wrote and tested code both online and locally.

When I got stuck during this learning stage, I used ChatGPT for hints, not complete solutions. I wanted to understand what I was doing and get the tests passing. I wrote the tests myself too.

## The simulation in hardware

The Python simulation was mainly the algorithm and a way to experiment with the behaviour. The Amaranth design was a different job. In Python, I could use libraries and write the algorithm. In Amaranth, I had to build everything from the low-level pieces and work all the way up.

I knew from the start that I would have to remake the simulation for hardware. I wasn't expecting to translate the Python code line by line. I wanted to make PENDENT with an ASIC, and getting the simulation working first meant I could work out what I wanted before dealing with all the hardware constraints.

The architecture developed while I was coding. I experimented with different particle counts rather than choosing the final number from some big plan at the beginning. The current GF180 configuration is described as a 256-particle Q4.12 PIC/FLIP design with a five-stage simulation pipeline.

### Fixed-point arithmetic

In Python, I could use normal floating-point values. In hardware, I needed to think about how numbers were represented and how wide each signal needed to be.

I used Q4.12 fixed-point arithmetic. That means the numbers have a fixed number of fractional bits. Multiplication produces a wider result with more fractional bits, so the result needs to be shifted back to the expected scale.

Simple enough, right?

Except getting the bit widths, signedness, shifts, and overflow behaviour correct took quite a bit of debugging.

### Not every test passed

I want to be clear about the test results. Some individual modules and simulations passed. That doesn't mean every integration test, gate-level test, precheck, or physical-design step passed. They are different stages, and I shouldn't describe them all as one big "passed".

### A note about AI

I also want to be honest about something.

The ASIC community has a restriction against AI-generated code. The reasoning is understandable: if AI writes your HDL and tests, you might end up with something you don't actually understand.

During the early Amaranth learning exercises, I used ChatGPT for hints when I got stuck. I wrote those tests myself and wanted to understand the modules rather than just copy a solution.

Later, when the project got much bigger and time was running out, I used AI more heavily. It helped generate parts of the reference implementation and parts of the Amaranth implementation. I also used it to explain concepts, explore approaches, and help debug errors. I didn't write every line of HDL myself.

I still had to work through the integration, understand how the modules connected, make design decisions, and test what was being built. Some tests passed and some didn't. I initially didn't want to mention this because I didn't want the project to be seen as an AI project.

But leaving it out wouldn't be honest. AI helped me move faster, but I still have a lot to learn, and I don't want to pretend I wrote every part myself.

### What does getting onto the chip mean?

Hack Club has a 1×1 slot on the [wafer.space GF180MCU Run 3 MPW](https://wafer.space/price.html), with support from [DeepAI](https://deepai.org/). The idea is to put over 100 student designs into separate tiles on one shared chip, multiplex them onto the IO pins, and manufacture the combined design.

So my design isn't going to be a whole chip by itself. It is one chunk of the shared chip, alongside everyone else's designs. The event plans to send participants a chip and breakout board containing the designs.

The event also asks us to make a Tiny Tapeout GF180 design, write up how it works, and test it on an FPGA with a logic analyzer before submitting it for the shared chip. That FPGA testing is my next step.


## The actual pendant hardware

The ASIC is only one part of the pendant. I still need the LEDs, sensors, memory, battery, and all the supporting electronics.

The current hardware plan includes:

- 216 monochrome LEDs in a circular arrangement, with no centre LED.
- An LED driver.
- A LIS2DW12 accelerometer for movement detection.
- ESP-PSRAM64H external PSRAM, shared between the RP2040 and ASIC.
- W25Q16JV QSPI flash, which I believe is for the RP2040 firmware, based on the devboard guide I followed.
- A rechargeable battery and power circuitry.

The idea is that when the pendant is lying face-down and not being used, it should go to sleep. Then, when someone shakes it, it wakes up.

### Memory: shared working memory and RP2040 flash

There are two different memory chips in the design, and they have different jobs.

#### ESP-PSRAM64H — shared working memory

The ESP-PSRAM64H provides 64 Mbit (8 MB) of external PSRAM. It is intended to be accessible to both the RP2040 and the ASIC. The ASIC uses it as working memory for the simulation; the RP2040 also has access to it.

<Figure
  src="https://cdn.hackclub.com/01a1c7b2-2596-738b-a631-a399bee432cb/Memory.png"
  alt="ESP-PSRAM64H memory schematic"
  caption="The external PSRAM connection."
/>

#### W25Q16JV — RP2040 flash

The other chip is the W25Q16JV. It provides 16 Mbit (2 MB) of QSPI flash. I believe this is for storing the RP2040 firmware, based on the [devboard guide](https://kaipereira.com/journal/build-a-devboard) I followed. I haven't independently confirmed every detail of that part yet.

<Figure
  src="https://cdn.hackclub.com/01a1c7b2-270f-77d8-9e2a-894a4167fdc5/QSPI_Flash.png"
  alt="W25Q16JV QSPI flash schematic"
  caption="The QSPI flash circuit."
/>

So the important distinction is:

- **ASIC:** performs the fluid simulation.
- **RP2040:** handles the chip-side communication and has access to the shared PSRAM.
- **PSRAM:** working memory shared by the RP2040 and ASIC.
- **QSPI flash:** intended for the RP2040 firmware.

## Things I learned

A few things I learned from all this:

- Getting a simulation working in Python is very different from implementing it in hardware.
- Amaranth made HDL easier to approach, but it didn't remove the need to understand hardware.
- Fixed-point arithmetic is more annoying than I expected.
- Passing one module's test doesn't mean the whole system works.
- A design can work in simulation and still fail during synthesis or physical design.
- Documentation is important. I should have written down more things while working instead of trying to remember everything later.
- PCB design is a whole separate learning curve.
- AI can speed things up, but it doesn't replace understanding what you're building.

And probably the biggest thing: there is a LOT of work between having an idea and getting an actual chip.
